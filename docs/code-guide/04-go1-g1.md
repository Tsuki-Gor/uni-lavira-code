# 04 · Go1 与 G1：从任务指令到机器人轨迹

本页沿着一次“走到门口”的任务阅读 Go1 和 G1。两端现在都进入 `LaViRAAgent.run`，共用 `CameraRobotRuntime`；相机、机器人 SDK、iPlanner 和底层运动控制仍由各端维护。要看清重构边界，应当分开问两件事：**为什么选择这个目标，由 LaViRA 决定；怎样取得图像并走向目标，由运行环境完成。**

先读 [接口契约](03-runtime-contract.md)，再沿本页链接进入源码。这里解释的是现有控制流，不是现场操作说明；文中的动作路径没有在真实机器人上验证。

## 1. 谁创建机器人，谁提交任务

Go1 的 [`main`](../../real-world-code/unitree_go1/main.py#L166) 解析配置并构造 `RobotController`，再选择交互模式或命令行任务，最后负责停止和清理。G1 的 [`main`](../../real-world-code/unitree_g1/main.py#L186) 还在分发任务前调用 `high_stand()`。这些初始化动作没有进入共享算法包。

命令行链路很短：[`Go1.run_headless`](../../real-world-code/unitree_go1/main.py#L139) / [`G1.run_headless`](../../real-world-code/unitree_g1/main.py#L165) 从参数取得任务名和指令，调用 `TaskFactory(name)` 找到任务类，传入已经创建好的机器人，然后执行 `task.run()`。工厂只是一个注册字典的查找函数，见 [`TaskFactory`](../../real-world-code/unitree_go1/tasks/__init__.py#L14)，并不是动态插件系统。

Web 模式多了一层任务线程：[`Go1.start_new_task`](../../real-world-code/unitree_go1/robot/nav_controller.py#L54) / [`G1.start_new_task`](../../real-world-code/unitree_g1/robot/nav_controller.py#L56) 默认构造 VLN 任务，把它交给后台线程运行，并将状态发送给界面。`nav_controller` 管的是旧应用的线程和界面交接，没有另一份 LA/VA 导航循环。

```text
main / Web 控制器
  → TaskFactory → 旧任务包装类
  → LaViRAAgent.run(Task, runtime)
  → CameraRobotRuntime → RobotController → 相机 / iPlanner / 运动接口
```

将来通用 Agent 接管设备时，可以在创建好机器人和 runtime 后直接调用共享核心，不必经过这些旧应用入口。现有任务包装类则继续维持原来的启动方式。

## 2. 旧任务类现在只组装哪些对象

打开 [`Go1.VLNTask.__init__`](../../real-world-code/unitree_go1/tasks/vln.py#L18) 和 [`G1.VLNTask.__init__`](../../real-world-code/unitree_g1/tasks/vln.py#L18)，会看到四个对象依次接起来：模型客户端、平台推理配置、共享 Agent、相机运行适配器。

平台内的 [`Go1.navigation_api`](../../real-world-code/unitree_go1/robot/navigation_api.py#L7) 与 [`G1.navigation_api`](../../real-world-code/unitree_g1/robot/navigation_api.py#L7) 只把 `Config` 传入共享推理类。真正的模型消息、解析和提示词已分别放到 [`lavira/reasoning/go1.py`](../../lavira/reasoning/go1.py#L104) 与 [`g1.py`](../../lavira/reasoning/g1.py#L112)。保留不同推理配置，是为了保留两端原有策略差别。

运行时，旧包装类的核心操作是：

```python
self.result = self.agent.run(
    Task(self.instruction, self.task_kind, reuse_runtime_history=True),
    self.runtime,
    cancellation=self._cancellation,
)
```

这段来自 [`Go1.VLNTask.run`](../../real-world-code/unitree_go1/tasks/vln.py#L41)，G1 相同。`finally` 再把核心的 step、TODO、visited_targets 写回旧字段，以兼容原来的读取方式。`stop_task()` 设置 `Event`，不直接执行物理急停。

两端的 ObjectNav 都只是改变 `task_kind` 的子类，见 [`Go1.ObjectNavTask`](../../real-world-code/unitree_go1/tasks/object_nav.py#L10) 和 [`G1.ObjectNavTask`](../../real-world-code/unitree_g1/tasks/object_nav.py#L10)。因此三类任务共用导航循环；ObjectNav 没有新增另一套设备接口。

## 3. 全景如何交给 LA

每轮从 [`LaViRAAgent.run`](../../lavira/agent.py#L82) 的 `observe_panorama(step)` 开始。相机适配器调用机器人的 `capture_all_directions`，再把落盘图像包装成 `Frame(path=..., heading_degrees=...)`。它返回的 `Panorama` 同时携带旧机器人累积的 iPlanner 图片路径，见 [`observe_panorama`](../../navigation_runtime/camera_robot.py#L27)。核心是否采用这些历史，取决于后文的兼容选项。

Go1 的底层采集可以按配置取四个方向，但旧任务装配只向 LA 提供前、右、左三个方向；“相机采过”不等于“模型实际看过”。具体采集见 [`Go1.capture_all_directions`](../../real-world-code/unitree_go1/robot/robot_controller.py#L303)，交给算法的方向表见 [`Go1.VLNTask`](../../real-world-code/unitree_go1/tasks/vln.py#L25)。

| 一次决策中的差别 | Go1 | G1 |
|---|---|---|
| 提供给 LA 的全景 | 前、右、左 | 前、右、后、左 |
| 首轮 TODO | 放入请求生成 TODO 的占位文本 | 先额外调用一次 LA 生成初始 TODO |
| LA 停止字段 | `action == "STOP"` | `stop`，兼容字符串 `"true"` |
| 后退方向 | 不在方向映射中，未知方向回到前方 | `behind` 对应右转 180° |
| 当前视图再次采集 | 等待 0.5 秒后再采一次，保留未检查第二次返回值的行为 | 单次采集 |
| 初始轨迹预留距离 | 1.5 米 | `Config.SAFE_DISTANCE`，默认 0.5 米 |

首轮 TODO 与停止字段的判断见 [`agent.py`](../../lavira/agent.py#L89)，方向与安全距离来自两端任务构造器；G1 默认值见 [`config.py`](../../real-world-code/unitree_g1/config.py#L91)。这些是显式保留的策略和参数差异，不要求两种本体产生相同动作。

## 4. LA 选方向，VA 选图像上的落点

LA 接收指令、TODO、当前全景和允许使用的轨迹图片，返回方向、目标描述与停止意图。核心更新 TODO，再通过 `runtime.turn()` 调用设备转向。适配器约定正角度向左、负角度向右，实际速度和转向控制留在机器人中，见 [`turn`](../../navigation_runtime/camera_robot.py#L40)。

转向后，核心通过 `observe_current()` 获得图像，再调用 VA。Go1 把 LA 的地标与进展描述交给 VA；G1 将方向与 reasoning 拼成战略目标，见 [`agent.py`](../../lavira/agent.py#L140)。VA 接口输出的 bbox 已经是图像像素坐标：Go1 按 `[0,1000]` 直接缩放；G1 在最大坐标不超过 1000 时缩放。后者可能误判本来就是小于 1000 的像素坐标，是保留的旧规则，见 [`Go1 转换`](../../lavira/reasoning/go1.py#L253) 和 [`G1 转换`](../../lavira/reasoning/g1.py#L272)。

核心随后选定一个导航像素，见 [`agent.py`](../../lavira/agent.py#L166)：

- Go1 取 bbox 水平中心、从顶部向下约 75% 的点。
- G1 取 bbox 底边中心，并限制纵坐标不超过深度图底边。
- 没有四元素 bbox 时，默认目标为机器人坐标系前方 1.5 米。
- 有 bbox 时，生成 `PixelGoal(view, u, v, fallback=RelativeGoal(1.5, 0))`。

停止意图也有明确时序：LA 与 VA 的停止结果会合并；停止且没有有效 bbox 时结束，有有效 bbox 时仍会先尝试执行这一段导航，再结束。Go1 还保留执行后的等待。这意味着 `STOP` 不是一条直接下发给电机的停止指令。

## 5. 像素怎样成为米制目标：读清单位和快照例外

[`observe_current`](../../navigation_runtime/camera_robot.py#L48) 返回 BGR 图像、原始深度数组以及宽高，深度明确标为 `depth_unit="mm"`。它没有统一把整张深度图改成米；规划器仍按原有输入使用数组。

[`navigate`](../../navigation_runtime/camera_robot.py#L75) 收到 `PixelGoal` 后，通过机器人 `get_depth_value` 取得该点的米制深度。Go1 在邻域中取有效值的第 30 百分位，G1 同样取第 30 百分位但邻域大小和过滤阈值不同，见 [`Go1 深度采样`](../../real-world-code/unitree_go1/robot/robot_controller.py#L254) / [`G1 深度采样`](../../real-world-code/unitree_g1/robot/robot_controller.py#L883)。两者都在这里将毫米除以 1000。

适配器使用以下投影得到机器人平面的米制目标：

```python
goal_2d = (depth, -(goal.u - cx) * depth / fx)
```

第一个分量是向前距离，第二个是向左距离；这不是世界坐标。`fx/cx` 来自机器人当前相机状态。

这里仍有一个重要兼容边界：投影读取机器人当前的 `direction_images/current_camera` 缓冲和内参，没有强制使用 `goal.view` 内的那张深度快照。即使 `PixelGoal` 带有 `Frame`，当前适配器也不能承诺“推理图、投影深度、位姿是同一时刻”。源码在 [`camera_robot.py`](../../navigation_runtime/camera_robot.py#L82) 明确保留了此行为；将来改成严格快照需要单独评估与验证。

深度或内参不可用时，适配器使用 `PixelGoal.fallback`；没有 fallback 则报告 `projection_unavailable`。新算法不能假定任何像素都能投影成功。

## 6. 谁规划、谁执行、返回值说明什么

适配器将当前 RGB、原始深度和米制目标传给 `robot.planner_client.get_plan`。iPlanner 生成几何轨迹，机器人绘制轨迹图片；LaViRA 不需要了解规划服务的传输细节。

接着适配器按路径累计长度减去安全距离，从离散路径点中截取前段，再调用 `execute_trajectory`，见 [`camera_robot.py`](../../navigation_runtime/camera_robot.py#L97)。若路径长度不足预留距离，则返回 `within_safety_buffer`。这里是在已有离散点上截断，没有插值保证精确留下某个距离，因而不能把参数解释为物理安全保证。

低层连续重规划、轨迹跟随、速度与姿态控制仍在 [`Go1.execute_trajectory`](../../real-world-code/unitree_go1/robot/robot_controller.py#L576) 和 [`G1.execute_trajectory`](../../real-world-code/unitree_g1/robot/robot_controller.py#L1183)。这也是其他高层算法可以复用的执行能力。

正常执行路径返回 `ExecutionReport(execution_called=True)`，但没有可靠的 `arrived=True`。它证明调用过执行接口，不证明到达了目标、任务成功或机器人已经停止。原有执行异常可能进入完整轨迹的再次执行分支，见 [`camera_robot.py`](../../navigation_runtime/camera_robot.py#L127)；该行为没有在结构重构中顺便改写。

## 7. 新接口怎样隔离任务历史，旧入口怎样保留

旧机器人的 `iplanner_history` 会累积初始轨迹图和重规划图。现在 [`Task.reuse_runtime_history`](../../lavira/runtime.py#L10) 默认为 `False`：每次 `run()` 创建新的 `TaskState.trajectory_images`，当前任务只消费本任务执行过程中收到的图片路径。旧 Go1/G1 包装类显式设置 `True`，因此仍能沿用跨任务的机器人历史。

新接口的关键交接只有一个回调，见 [`agent.py`](../../lavira/agent.py#L184)：

```python
record_options["on_trajectory_image"] = state.trajectory_images.append
report = runtime.navigate(goal, state.step, **record_options)
```

运行适配器把回调传给初始轨迹绘制和执行函数。机器人每保存一张轨迹图片，仍追加到自己的历史，同时调用这个回调。Go1 的重规划 worker 捕获的是此次执行传入的回调，见 [`replan_worker`](../../real-world-code/unitree_go1/robot/robot_controller.py#L602)；G1 也把它传给后续绘图，见 [`G1 重规划`](../../real-world-code/unitree_g1/robot/robot_controller.py#L1373)。

这避免了按“当前正在运行的任务”猜测异步图片归属。旧任务结束后，迟到 worker 仍只持有旧列表；返回结果前，核心还复制一次 `trajectory_images`，见 [`agent.py`](../../lavira/agent.py#L223)，使迟到写入不改变已返回结果，也不会加入新任务的默认历史。机器人自身日志仍会累积，启用兼容选项的旧入口依然允许读取这些历史。

## 8. EQA、取消与阅读后的检查点

EQA 在同一个导航调用结束后进入 [`answer_question`](../../lavira/reasoning/eqa.py#L10)。Go1 读取前、右、左固定相机；G1 更新相机数据后读取前视图，见 [`observe_views`](../../navigation_runtime/camera_robot.py#L63)。共享问答代码沿用各端提示词和编码，调用 LA，返回 `answer/answer_error`；旧 [`Go1.EQATask`](../../real-world-code/unitree_go1/tasks/eqa.py#L13) / [`G1.EQATask`](../../real-world-code/unitree_g1/tasks/eqa.py#L13) 只负责保存最终 JSON。

当前取消是轮次边界上的合作式取消，不会打断每一个模型请求或底层动作；旧控制器切换任务只等待两秒，EQA 还保留导航取消后继续问答的行为。不要把线程启动成功、循环返回、`model_stop` 或 `cancellation_requested` 等同于物理停止确认。

想验证自己是否读懂，可分别沿三个问题回看：改变目标描述应读 `lavira/reasoning`；改变相机和单位应读 `CameraRobotRuntime` 及设备采样；改变轨迹跟随应读机器人控制器。一个高层算法替换应主要改变第一处和装配，而不复制其余两层。

相关离线证据集中在 [`test_navigation_loop.py`](../../tests/test_navigation_loop.py)、[`test_task_history.py`](../../tests/test_task_history.py)、[`test_delayed_trajectory_history.py`](../../tests/test_delayed_trajectory_history.py) 与 [`test_frame_metadata.py`](../../tests/test_frame_metadata.py)。它们核对旧行为、任务历史归属及数据说明，不替代真实相机、模型与机器人的联合运行。
