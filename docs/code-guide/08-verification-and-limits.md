# 08 · 验证证明了什么，还有哪些限制

本次验收证明：在固定观测、固定模型回复和替代外部依赖的离线条件下，四个平台的三类任务已进入共享核心，保留被覆盖的请求和执行次序；环境能力可以在不加载 LaViRA 的情况下被调用。它没有证明真实模型导航效果、完整 Habitat 部署或真实机器人执行成功。

本页解释代码提交 `9ed2fbf` 的收尾验证，文档提交 `31873f9` 记录了同一结果。此次阅读文档编写核对了现有测试源码及当时日志，没有为编写文档重新运行全部测试。

## 1. 为什么与原版对照，而不只测试新类

纯重构首先要回答：相同输入下，送给模型的消息和发给执行器的动作是否改变。测试通过 `git show 215e7ac:<路径>` 读取旧实现，在固定回复和观测下同时执行原版与当前代码，然后比较请求、结果及调用轨迹。

客户端对照从 [test_clients.py](../../tests/test_clients.py#L30) 开始；机器人推理使用 [original_module](../../tests/test_ground_reasoning.py#L1) 加载原文件。图像相关测试使用 NumPy、Pillow、OpenCV 实际编码，避免只比较占位字符串而漏掉图像内容、尺寸或顺序变化。

Habitat 由于完整导入需要较重的仿真依赖，[rollout_methods](../../tests/test_habitat_loop.py#L24) 从 AST 提取原版和新版的实际方法体执行，外部环境、地图、局部规划器及 Tensor API 使用替身。这样覆盖实际 rollout 分支，但不能推导真实 Habitat 版本、GPU 渲染或传感器接口一定兼容。

原版也可能有缺陷。对照相同，只证明保留了被覆盖行为；它不会自动把旧行为判定为合理。新增任务历史隔离则按用户确认的新接口契约测试，同时继续检查旧入口兼容。

## 2. “19 组测试”具体指什么

这里的 19 指 `unittest` 报告的 19 个测试方法。许多方法内部遍历多平台、任务和故障场景，所以它不是只有 19 次导航，也不能把下面所有子场景相加后称为独立真实实验。

| 测试入口 | 主要证据 | 仍被替换或未覆盖的部分 |
| --- | --- | --- |
| [机器人客户端](../../tests/test_clients.py#L30) | 共享类及三个旧包装在 6 类条件下共 24 个对照；参数、LA/VA 路由、system 消息、重试、统计和错误传播一致 | OpenAI SDK 返回固定结果，没有请求服务 |
| [Habitat 客户端](../../tests/test_habitat_client.py#L18) | 10 组请求、重试和错误字符串对照 | 服务、网络和模型行为 |
| [地面推理](../../tests/test_ground_reasoning.py#L46) | 三种 profile 的真实消息、图像载荷、bbox 解析及旧辅助入口保持一致 | 回复预设，不评价模型识别能力 |
| [Habitat 推理](../../tests/test_habitat_reasoning.py#L52) | 三任务共 24 组历史、TODO、回溯、停止和 EQA 检查，prompt 字节一致 | 仿真观测和在线模型 |
| [Go1/G1 导航轨迹](../../tests/test_navigation_loop.py#L133) | 两平台共 16 条轨迹；方向、最后接近、缺框、规划/采图失败和取消次序 | 机器人和规划执行使用替身 |
| [Go1/G1 ObjectNav/EQA](../../tests/test_navigation_loop.py#L21) | 共 14 条轨迹；导航后问答、缺图、错误、原始答案及保存行为 | 真实问答正确率、相机和文件部署路径 |
| [完整任务契约](../../tests/test_navigation_loop.py#L51) | 状态分离、进度、取消、预算、EQA 答案、非法目标；执行返回不被误写成物理停止 | 模型或控制器阻塞中的即时取消 |
| [Cobot 任务循环](../../tests/test_cobot_loop.py#L18) | VLN/ObjectNav 18 条、EQA 12 条；视角、复位线程次序、TODO、停止及问答 | 机械臂、底盘和动态导航使用替身 |
| [Habitat rollout](../../tests/test_habitat_loop.py#L45) | 62 条实际方法体对照；三任务、转向、停止拒绝、回溯、超时、预算和 NavDP 缓存 | 地图、Tensor、环境和局部规划器使用替身 |
| [Habitat 取消与替代算法](../../tests/test_habitat_loop.py#L68) | 取消结果；替代算法使用同一地图运行时的观测、投影和执行 | 没有在真实仿真中运行第二种导航算法 |
| [Habitat 环境装配](../../tests/test_habitat_environment.py#L124) | 三任务 × FMM/NavDP 六组配置，实际主机和旧评测器构造、环境创建及 reset | Habitat、网络、分割/建图模型等外部依赖使用替身 |
| [旧任务完整调用链](../../tests/test_environment_boundaries.py#L20) | 三个真实 TaskFactory 的九种任务，实际客户端→推理→核心→执行器跑完一轮 | 仅替换模型 SDK、机器人及等待，不构造硬件 |
| [机器人独立导入](../../tests/test_environment_boundaries.py#L134) | 屏蔽 LaViRA、模型 SDK 等后仍可导入实际机器人模块；不连带导入导航算法 | 只导入，不初始化控制器或通信连接 |
| [相机帧元数据](../../tests/test_frame_metadata.py#L11) | Go1/G1 原始毫米深度、数组身份及图像尺寸保持一致 | 真实深度设备与时序同步 |
| [云台帧元数据](../../tests/test_frame_metadata.py#L43) | Cobot 米制深度、不同视角尺寸、缺图/缺深度如实描述 | 真实 ROS 消息和机械臂采样 |
| [替代算法与执行记录](../../tests/test_task_history.py#L15) | 屏蔽 LaViRA 后实际相机执行器可导航；规划图、重规划图回调只报告本次执行，短轨迹/规划失败有对应证据 | iPlanner 规划和物理执行用替身 |
| [新旧任务历史](../../tests/test_task_history.py#L63) | Go1/G1 新任务默认独立、旧模式累计；同一运行时连续调用不会隐式混用历史 | 不管理记录文件的删除和长期存储 |
| [迟到回调隔离](../../tests/test_delayed_trajectory_history.py#L18) | 上个任务的延迟图片不进入下个任务，也不改变已经返回的列表 | 可控回调次序，不覆盖所有实际线程调度 |
| [真实 Go1 重规划方法](../../tests/test_delayed_trajectory_history.py#L73) | 实际 `execute_trajectory` 方法体中两次工作逆序完成，图片仍归属原执行回调 | 调度、时钟、规划和记录替换；不构造或驱动机器人 |

这些检查组合起来覆盖三条不同证据链：旧行为是否保留、新接口是否表达正确、旧入口是否实际接上新实现。单独“能 import”或仅替换 `LaViRAAgent.run` 的装配测试，覆盖不到真实客户端与推理连起来后的问题。

## 3. 两处抽取回归如何被发现和修复

NavDP 原有轨迹缓存存储在环境主机上。抽取执行器后，存在性检查误查了执行器自身，导致每步重新规划；提交 `02928e7` 把检查恢复到 host。测试中的 `navdp_cache` 使用连续轨迹，对三类任务都比较旧版与新版，从而验证原有五步缓存窗口。

新 `Frame` 的默认深度单位是米，但 Go1/G1 返回的原始数组是毫米。提交 `9018976` 明确标注 `mm` 并补齐数组尺寸，没有把原始数组改写成米，也没有修改控制器已有换算。Cobot 当前深度已是米，所以保留 `m`。

这两项属于重构引入的错误，修复目标是恢复原语义。它们与下面的旧问题不同，也与用户另行确认的新接口历史隔离不同。

## 4. 独立导入与临时 wheel 的证据范围

共享包从临时源码副本离线构建，避免把构建产物写入工作区。验证离开仓库目录，并屏蔽平台模块后，wheel 内 23 个 Python 模块（含包根）仍可导入；再屏蔽 `lavira`，三个运行时适配器仍可重新导入。

这说明包内容齐全、被检查导入路径没有反向依赖平台或算法。它没有检查所有延迟执行路径，也没有包含完整 Habitat 环境主机、机器人驱动或各平台依赖的安装。

当时的证据文件在项目专用临时目录，可能随临时目录清理而消失；长期结论保存在 [迁移与验收说明](../lavira-migration.md)：

```text
/data1/home/gzj/tmp/uni-lavira-code/final-root-tests.log
/data1/home/gzj/tmp/uni-lavira-code/completion-wheel-check.log
/data1/home/gzj/tmp/uni-lavira-code/completion-wheels/uni_lavira_core-0.1.0-py3-none-any.whl
```

该 wheel 的 SHA256 为 `cbeaee0cfc96c7d37d2ebd04af4dfd7164758e2e9a68c29e673bacc91e024b76`。它标识当时那一个构建产物；源码修改或重新打包后应重新核对，不能继续沿用这个哈希声称验证了新文件。

## 5. Python、依赖和 CodeGraph 检查如何理解

收尾测试实际使用 Python 3.10；依赖为已有 OpenAI 2.2.0、NumPy 1.23.5、Pillow 10.4.0、OpenCV headless 4.10.0.84。69 个改动 Python 文件通过 Python 3.8 语法解析和编译检查，说明没有被该检查识别出的语法不兼容；**不是在 Python 3.8 解释器里运行过这些测试**。

打包配置仍声明 Python `>=3.8`，真正部署到 Habitat 原环境时仍需核对依赖版本及实际运行。离线测试使用 headless OpenCV 不等于所有图形或显示路径都被覆盖。

收尾的 `codegraph sync` / `status` 报告索引最新，规模为 320 个文件、5,162 个节点、10,441 条边。这个数字是当时索引范围的快照，后续补文档可能改变它。CodeGraph 用于定位调用与依赖，不能替代运行检查，更不能证明模型或硬件有效。

`git diff --check` 通过说明没有检查出的空白格式问题。它不检查任务语义；与代码评审、行为对照和导入测试结合才有意义。

## 6. 如何重跑当前离线验收

在仓库根目录运行以下明确限定到根 `tests/` 的命令，结果应同时检查测试数量、失败和跳过：

```bash
TMPDIR=/data1/home/gzj/tmp/uni-lavira-code \
/data1/home/gzj/tmp/uni-lavira-code/test-env/bin/python \
-m unittest discover -s tests -v
```

收尾日志是 `Ran 19 tests in 18.761s`、`OK`，没有跳过。这个解释器路径是本机临时环境；换机器应按项目已有依赖准备环境，不应把路径本身当成仓库分发的一部分。

部分测试在图像依赖缺失时会 `skipTest`，因此只看到退出码为零还不够。原版对照还依赖本地 Git 历史中存在 `215e7ac`。不要对整个仓库做无筛选的递归测试发现，平台目录中包含机械臂、键盘控制或整机初始化脚本。

## 7. 九项仍保留的旧行为问题

以下问题没有作为本次抽取的附带修复。若要调整，先确认触发条件和新行为，再单独提交；详见 [设计中的待决清单](../lavira-core-design.md#待用户决定的行为问题)。

| 问题 | 对调用者意味着什么 | 后续需要确定的变化 |
| --- | --- | --- |
| JSON 解析失败或 bbox 缺失后可能默认移动 | “没有识别到目标”不必然等于停止 | 停止、重问还是保留默认前进 |
| G1/Cobot 按坐标是否 ≤1000 推断归一化 | 小图像像素框可能被重复缩放 | 明确坐标格式并修改兼容规则 |
| Go1/G1 缺少可信到达返回 | `execution_called=True` 不证明到达目标 | 增加可验证的到达状态及来源 |
| 取消不覆盖所有阻塞，EQA 仍可能继续 | 取消请求不等于模型请求或物理动作已停止 | 取消传播、等待和问答收尾策略 |
| 实时深度/默认位姿可能与选定图像不同步 | `PixelGoal` 绑定图像仍不能保证旧执行端使用完全同步传感数据 | 观测快照、缺定位策略和投影约束 |
| Habitat `get_model_info()` 读取未定义旧属性 | 当前导航调用链不使用它，不应把它当可靠信息接口 | 明确信息字段并单独修正 |
| Go1/G1 截断轨迹的异常分支可能重放动作 | 原执行抛错也可能被捕获并执行原轨迹 | 缩小异常范围，禁止不确定的动作重放 |
| Habitat working memory 图像与文字标签不符；停止确认沿用 VLN 全局 prompt | 输入保留了原不一致，任务专用停止提示未统一 | 分别决定历史图来源及任务 prompt |
| Habitat CPU 历史位姿可能引用共享数组 | 后续地图更新可能改变历史位姿，影响回溯投影 | 是否冻结快照，并重新评估轨迹差异 |

任务历史隔离已经另行获得确认并实现，因此不再列为待决问题。它解决的是 Go1/G1 新调用的 iPlanner 图片归属；不会顺带解决 Habitat 的 CPU 位姿共享引用，也不会增强物理取消。

## 8. 哪些验收还没有做

模型在线调用没有执行，因此没有关于真实 API 可用性、模型质量、导航成功率或 EQA 正确率的新结论。固定模型回复只用来验证程序在该回复下的处理。

没有启动完整 Habitat/Docker、真实数据集和 GPU 渲染链。当前环境主机构造测试替换了外部依赖；FMM/NavDP 通过离线分支检查，也不意味着其真实模型、服务和部署已经成功。原已移除的 Habitat iPlanner 后端继续禁用，没有在此次重构中恢复。

服务器上没有机器人，没有执行 ROS 启动、真实传感采样、底盘运动或机械臂运动。未来将代码放到机器人上后，需要验证单位/坐标、采样次序、执行反馈和取消效果；现有测试不会把替身返回的 `True` 升格为物理到达证据。

所以本阶段可以据此审核“代码和依赖边界是否已抽取、兼容分支是否保留”，实际部署和效果评测仍是下一层工作。接入通用 Agent 时也应分别记录算法结束原因、取消请求、执行反馈和外部环境成功指标。
