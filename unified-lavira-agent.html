1. 目标与范围

消除各平台分别维护的 LaViRA 高层导航流程。共享的是推理、记忆与任务控制，平台仍使用现有传感器、运动控制、规划器和评测入口。 第一阶段先接通 VLN，再让同一核心承接 ObjectNav 和 EQA。

这一阶段交付

  • 可独立导入的算法包，不要求安装 Habitat、ROS 或机器人 SDK。
  • 完整任务调用、进度通知、取消请求和有明确语义的结果。
  • 四个平台、三类任务接入共享高层循环；平台入口负责组装。
  • 固定模型响应和观测下的行为对照，以及平台入口的离线接入检查。

已确认的限制

  • 保留各端模型请求、prompt、默认参数和策略差异。
  • 当前服务器没有机器人；测试不能证明真机到达或物理停止。
  • AirSim、自研无人机留待后续；不合并现有运行环境。
  • 行为修正、新增依赖交用户决定；只做本地提交。

2. 原方案需要修正的地方

原表述或遗漏代码事实与修订
所有端都能直接套用“四方向、LA → VA → 执行”Go1 用三方向，G1/Habitat 用四方向，Cobot 包括斜向的七个有效视角；停止、回溯和任务收尾必须成为共享循环的分支。
LA 表示停止，就确认并结束Go1/G1 的停止可能包含最后一次 bbox 接近；Habitat 接近后重新采集全景、二次确认，并保留失败累计三次强制停止。Cobot 的 LA STOP 则直接结束该导航循环。
回溯就是去旧 waypointHabitat 可在历史全景上重新 LA/VA，利用当时的深度和位姿生成新目标；另一配置才直接返回旧位置。
Adapter 接收 StrategicDecision/TacticalDecision，负责 confirm_stop这会让环境依赖 LaViRA。停止确认和决策解析属于算法；环境接收转角、像素目标及观测引用等通用执行输入。
Agent 调用 adapter.reset_episode用户已选择外部管理环境生命周期。主程序负责创建、reset、关闭环境；Agent 只重置本次任务的内部状态。
统一 client 就统一请求方式，统一 prompt 以 Habitat 为底本机器人客户端三份完全相同，可先合并；Habitat 的返回格式、请求参数、重试和失败返回不同。保留兼容策略，不能借抽包替换请求或 prompt。
历史轨迹图只是可视化Go1/G1 会把这些图送入 LA。历史图的生成、取样和次序属于行为对照范围。
空中平台 VA 都输出距离/高度AirSim 的实际入口有距离/高度输出；自研无人机实际流程也使用 bbox，且在转向前调用 VA。暂缓接入的理由是范围和执行差异，不能用错误的输出分类解释。
规划器、建图必须属于具体本体应与算法决策分开，但 FMM/NavDP/iPlanner 可作为可复用导航执行服务。第一阶段保持现有实现，不强制复制到每个驱动。

5. 一次导航任务怎样运行

flowchart TD
  A["外部准备环境，提交任务和能力"] --> B["初始化本次算法状态"]
  B --> C["取得观测，组装历史与 TODO，调用 LA"]
  C --> D{"策略决定"}
  D -->|导航或最后接近| E["选择视角并转向，调用 VA"]
  D -->|回溯| F["取历史观测，按配置重规划或返回旧位置"]
  E --> G["从 bbox 选目标，调用导航执行能力"]
  F --> G
  G --> H["更新记忆、TODO、进度与预算"]
  H --> I{"是否需要停止确认"}
  I -->|否，继续| C
  I -->|是| J["采集新观测，由算法确认停止"]
  J -->|未确认且未到旧策略上限| C
  J -->|确认或达到旧策略上限| K["按任务完成 EQA 等收尾"]
  D -->|立即结束的兼容分支| K
  H -->|达到预算或环境结束| K
  K --> R["返回结束原因、答案及执行证据"]
取消在已有任务检查点处理。此图展示共享流程及必要分支，不表示各平台都执行停止确认或回溯。

只有一个高层任务驱动器。导航执行服务仍可有高频控制循环，模型重试仍可有自己的循环；这些不是重复的 LaViRA pipeline。 VLN 和 ObjectNav 使用任务对应的提示与结束规则，EQA 增加问答收尾，不能另起一套高层导航循环。

6. 观测、执行与结果契约

边界必须说明的语义
观测图像内容及通道约定、深度单位、图像尺寸、视角、采集时位姿/相机参数。历史图必须与历史深度和位姿绑定；不能拿新深度解释旧 bbox。
转向和像素目标角度单位与正方向、像素坐标所属图像、越界处理和锚点策略。归一化 bbox 的原有识别规则保留在兼容解析中，不让驱动猜测模型输出。
位置目标目标与参考坐标系一起传递；Habitat 地图格、机器人局部米制目标、世界位置不能混为裸二元组。
执行反馈区分动作返回、确认到达、超时、失败、状态未知；允许旧执行器没有到达证据。不得把返回 None 自动解释为到达。
任务结果分别表达算法的结束原因、问答答案和环境成功指标；模型说 STOP 不等于导航成功。
取消请求取消、任务循环已响应、底层停止已确认是不同事实。第一阶段保留现有阻塞段与收尾规则，不能承诺即时制动。
生命周期外部创建、reset 和关闭环境；每次完整任务调用持有独立算法状态。入口不应暗中复用上个任务的记忆。
部分旧执行器会在动作执行时读取实时深度，Habitat 的 CPU 历史位姿也可能保留共享引用。 本次保留这些兼容语义；绑定采集帧或冻结位姿会改变目标和轨迹，需要另行决定。详见设计说明中的待决问题。

7. Habitat 的迁移边界

从 VLMReasoningAgent 提取请求、解析、TODO 与记忆， 从 评测器 rollout 分出高层任务推进。 环境 reset、数据集、地图、底层动作与指标仍归外部；采集全景产生的 12 次动作及其预算也必须记录。 HabitatEnvironment 提供独立环境能力，旧评测器只组装它和 LaViRA。

  • 保留“停止信号 → 转向/VA → 最后接近 → 新全景二次确认”的顺序。
  • 回溯重规划使用旧视图、深度和位姿；重访记忆仍保存来源关系。
  • 楼梯信息转为明确的执行提示；执行服务不读取 agent.stair 等算法内部对象。
  • 历史图既用于推理也用于日志。用外部提供的记录回调承接可视化，不让核心导入 Habitat logger 或 visualizer。
  • EQA 答案交给评测器；保留该任务与普通 STOP 不同的结束处理。

8. 三台机器人的迁移边界

三个 ai_client/vision_client.py 可直接去重。 robot/navigation_api.py 实际包含 LaViRA prompt 和解析，应迁入核心； tasks/vln.py 的高层流程并入共享驱动器，原任务类保留参数转换和兼容入口。

  • Go1：保留三视角、转向后再采图的顺序、VA 锚点、轨迹末端安全距离、历史图与停止后的等待。
  • G1：保留独立初始 TODO 请求、后方视角、bbox 归一化识别、配置的安全距离和现有控制路径。
  • Cobot：保留全景时的机械臂复位线程、七方向、LA 直接停止、到达后更新 TODO。VLN/ObjectNav 的重复循环合并。
  • 三端 EQA：问答与导航共用任务状态和结果接口；现有取消后仍可能进入问答的问题先列出，不暗改。

相机、机械臂、iPlanner 调用及速度控制留在可迁出的执行代码中。 一个最小替代算法的离线检查应能使用这些通用能力，不导入 LaViRA 的 prompt 或决策类型。

9. 验收与待决定的问题

第一阶段以离线证据验收：保存固定响应，比较原入口与新核心的请求内容、图像顺序、决策、动作顺序和结束原因； 检查四个平台 × 三类任务的接入。模型服务、真实仿真和真机分别记录，未运行的层级明确标为未验证。

检查能证明的内容
请求与轨迹回放给定输入下 prompt、请求参数、策略分支、动作次序未漂移；不证明模型在线输出相同。
导入与依赖检查核心不依赖 Habitat、ROS、SDK；环境契约不依赖 LA/VA 类型。
任务与入口测试VLN/ObjectNav/EQA 实际接入核心；覆盖停止、回溯、空观测、超预算和已有取消检查点。
硬件部署回归需要未来在相应机器人和运行环境上完成；当前不作为已经取得的证据。
已发现但本次不自行修正：解析失败后的默认移动、bbox 缩放歧义、旧执行器到达证据不足、取消后仍问答、停止旧任务等待不足。 逐项说明影响，待用户决定后用独立提交处理。
